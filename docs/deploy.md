# Деплой: постоянная ссылка на игру

Схема раздвоенная: **клиент** живёт на GitHub Pages по постоянному адресу, а
**сервер** — на твоей машине и выставляется наружу туннелем. Играть можно только
когда сервер и туннель запущены.

```
игрок → https://gern133.github.io/warfront/      (статика, GitHub Pages)
           └── wss:// … (VITE_WS_URL) → туннель → localhost:8080 (твой сервер)
```

---

## 1. Почему ссылка «умирает» и что именно умирает

Умирает **не** Pages. Pages — статика, она стоит вечно. Умирает **адрес туннеля**,
который вшит в клиент.

Ключевой момент: `VITE_WS_URL` — это переменная **времени сборки** (Vite подставляет
её в бандл). Значит адрес туннеля физически лежит внутри опубликованного JS. Поменялся
туннель → надо **пересобрать и переопубликовать клиент**, иначе он продолжит стучаться
на мёртвый адрес.

Отсюда два класса поломок:

| Симптом | Причина | Что делать |
|---|---|---|
| Страница открывается, но игра не подключается | адрес туннеля сменился или туннель не запущен | раздел 2 |
| Страница не открывается вообще (404) | Pages выключен или деплой упал | раздел 4 |

**Одноразовые туннели умирают всегда.** `*.trycloudflare.com` (это
`cloudflared tunnel --url`) и ngrok без `--url` выдают адрес заново при каждом
запуске. Именно так ссылка и умерла в прошлый раз. Лечится статическим доменом —
раздел 3.

---

## 2. Ссылка умерла — что делать сейчас

Одной командой:

```bash
npm run build && npm start        # в отдельном терминале: сервер на :8080
npm run deploy                    # туннель + переменная + пересборка Pages
```

`npm run deploy` (`tools/publish.sh`) делает всё по порядку:

1. проверяет, что сервер слушает `:8080` (иначе не даст публиковать мёртвое);
2. поднимает ngrok (или переиспользует уже поднятый) и узнаёт публичный адрес
   через локальное API агента `http://127.0.0.1:4040/api/tunnels`;
3. проверяет туннель запросом — должен ответить `200`;
4. пишет `wss://…` в переменную репозитория `VITE_WS_URL`;
5. запускает workflow `deploy-pages.yml`, чтобы клиент пересобрался с новым адресом.

Проверить, что новый адрес реально уехал в опубликованный клиент:

```bash
JS=$(curl -s https://gern133.github.io/warfront/ | grep -oE '/warfront/assets/index-[A-Za-z0-9_-]+\.js' | head -1)
curl -s "https://gern133.github.io$JS" | grep -oE 'wss://[a-z0-9.-]+' | sort -u
```

Должен вывести текущий адрес туннеля и ничего больше.

### Вручную, если скрипт не подходит

```bash
ngrok http 8080                                   # взять https-адрес из вывода
gh variable set VITE_WS_URL -R gern133/warfront --body "wss://<адрес>"
gh workflow run deploy-pages.yml -R gern133/warfront
gh run watch -R gern133/warfront
```

`wss://`, а не `https://` — клиент открывает WebSocket.

## 3. Чтобы больше не умирала: статический домен

Бесплатный аккаунт ngrok даёт **один статический домен**, который не меняется между
перезапусками. С ним пересобирать клиент больше не нужно **никогда** — достаточно
поднять сервер и туннель.

1. [ngrok Dashboard](https://dashboard.ngrok.com) → **Domains** → Create domain →
   получить что-то вида `warfront.ngrok-free.app`.
2. Один раз опубликовать клиент с этим адресом:
   ```bash
   NGROK_DOMAIN=warfront.ngrok-free.app npm run deploy
   ```
3. Дальше каждый игровой вечер — только две команды:
   ```bash
   npm run build && npm start
   ngrok http --url=warfront.ngrok-free.app 8080
   ```

Пока домен не зарезервирован, `npm run deploy` в конце честно предупреждает, что
адрес эфемерный.

## 4. Если не открывается сама страница

Проверить по шагам:

```bash
gh api repos/gern133/warfront/pages                     # включён ли Pages
gh run list -R gern133/warfront -w deploy-pages.yml -L 5 # падал ли деплой
curl -o /dev/null -w '%{http_code}\n' https://gern133.github.io/warfront/
```

Что должно быть:

- `pages` отвечает объектом, где `"build_type": "workflow"` и `"source.branch": "main"`.
  Если 404 — Settings → Pages → Source: **GitHub Actions**.
- Прогоны `deploy-pages.yml` — `success`. Триггеры: пуш в `main` и ручной запуск.
- `curl` — `200`.

**Про `base` в Vite.** Pages раздаёт сайт из подпапки `/warfront/`, поэтому
`vite.config.ts` подставляет базовый путь только когда сборка идёт для Pages:

```ts
base: process.env.GITHUB_PAGES ? '/warfront/' : '/',
```

Workflow выставляет `GITHUB_PAGES: 'true'`. Если собрать без этой переменной и залить
на Pages, страница откроется, но все ассеты уйдут в 404 — белый экран. Локальная
сборка (`npm run build`) базу не меняет, потому что там статику раздаёт свой же сервер
с корня.

## 5. Что где лежит

| Что | Где |
|---|---|
| Workflow деплоя | `.github/workflows/deploy-pages.yml` |
| Скрипт публикации | `tools/publish.sh` (`npm run deploy`) |
| Базовый путь для Pages | `vite.config.ts` → `base` |
| Адрес сервера в клиенте | переменная репозитория `VITE_WS_URL` → `client/App.tsx` |
| Фолбэк без переменной | тот же `client/App.tsx`: `wss://<текущий хост>` при https, иначе `ws://<хост>:8080` |

Фолбэк объясняет, почему всё работает локально и через туннель к самому серверу
(`npm start` + cloudflared на 8080) без всяких переменных: клиент подключается к тому
же хосту, с которого его отдали. Переменная нужна ровно для раздельного хостинга,
когда клиент отдаёт Pages, а сервер живёт в другом месте.
