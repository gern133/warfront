# Производительность симуляции

Бюджет на тик — `100 мс` (`TICK_MS`, 10 тиков/сек). Тяжёлый случай: карта Земли
`1920×900` (1.73 млн клеток) и `293` игрока.

Оптимизации взяты из OpenFront — там те же проблемы решены на большем масштабе:
`src/core/game/TileTraversalScratch.ts` (штампы поколений), `GameMap.neighbors4`
(буферы вместо колбэков), `AStar.WaterHierarchical` (иерархический поиск),
`SmoothingWaterTransformer` (спрямление бинарным поиском), `UnitGrid`
(пространственный индекс).

## Как измерять

```bash
# профиль по функциям
node --cpu-prof --cpu-prof-dir=/tmp/prof --import tsx твой-скрипт.mjs
# времена тиков: средний / p50 / p99 / худший
```

Смотреть надо **не только средний тик**: средний был 0.86 мс при худшем `72 мс` —
то есть проблема была не в среднем, а в пиках, когда в один тик прилетала пачка
первых запросов на морские маршруты.

## Что сделано

### 1. Штамп поколения вместо очистки массивов

Грубый морской BFS делал `prev.fill(-2)` по **432 тыс.** блоков на КАЖДЫЙ маршрут,
хотя обходил малую часть сетки. Теперь у каждой клетки хранится «поколение»
посещения, а перед поиском просто инкрементируется счётчик — очистка не нужна
вовсе. У OpenFront это `bumpTraversalGeneration` / `tileTraversalScratch`.

Тот же приём уже использовался в точном поиске по воде (`fineGen`) и добавлен для
маски коридора (`corrGen`).

### 2. Грубый морской поиск: BFS → A*

Волна в ширину без эвристики обходила пол-океана — **18 % времени тика**. Замена на
A* с эвристикой Чебышёва (та же плоская куча на `Int32Array`, что и в точном
поиске) режет число раскрытых блоков в разы. У них для этого целый
`AStarWaterHierarchical` поверх кластерного графа; нам на сетке `960×450` хватает
обычного A*.

### 3. Спрямление пути: линейный проход → бинарный поиск

`smoothWaterPath` искал самую далёкую видимую точку линейно: O(n) проверок по O(n)
клеток каждая — то есть **O(n²)** на путь в тысячи клеток. Теперь бинарный поиск,
как `losSmooth` в их `SmoothingWaterTransformer` («binary search LOS smoothing»).

Видимость по воде не строго монотонна (за мысом может снова «открыться»), поэтому
бинарный поиск иногда останавливается на точку раньше абсолютного максимума — это
лишь лишний перелом на маршруте, каждый отрезок по-прежнему гарантированно водный.

### 4. Потолок на раскрытие и бюджет маршрутов за тик

- **Потолок раскрытия** в поиске по коридору: `200 тыс.` клеток с коридором и
  `60 тыс.` без него. Именно страховочный поиск без коридора мог обойти весь океан
  и давал пики. (В точном поиске такой предохранитель уже был — `EXPLORE_CAP`.)
- **`ROUTE_BUDGET = 2`** — не больше двух НОВЫХ морских маршрутов за тик. Готовые
  берутся из кэша бесплатно (порты статичны), так что ограничение задерживает лишь
  самую первую отправку судна по новой паре портов, на тик-другой.

### 5. Буфер соседей вместо колбэков в горячих циклах

`forNeighbors(c, fn)` создаёт замыкание на КАЖДУЮ клетку и мешает встраиванию.
В горячих местах (`buildFrontier`, `stepAttack`, `hasNeutralBorder`) заменено на
`neighbors4(c, buf)` с переиспользуемым `Int32Array(4)` — как `GameMap.neighbors4`
у них. В остальных местах (вызываются редко) `forNeighbors` оставлен: там читаемость
важнее.

### 6. Локальный поиск вместо перебора карты

`landingShore` (берег высадки для десанта) перебирал **все 1.73 млн клеток** карты
с замыканием на каждую — и вызывался на каждый запуск десанта. Заменён на
расширяющиеся кольца вокруг точки клика, как `bfsNearest` у них (у них ограничение
`maxDist = 50`). Запуск десанта: `13.5 → 7.7 мс`.

Предпосчитаны и вынесены в массивы `coastal` / `shore` / `ocean` / `waterId`
(см. [водную модель](./water.md)) — раньше «прибрежность» считалась четырьмя
чтениями массива на каждого соседа внутри цикла A*.

## Результат

| | до | после |
|---|---|---|
| средний тик | 0.86 мс | **0.75 мс** |
| p50 | 0.32 мс | 0.31 мс |
| p99 | 12.1 мс | 10.4 мс |
| **худший тик** | **72.4 мс** | **32.9 мс** |

4000 тиков, карта Земли, 293 бота. Важно, что это уже **с новой водной моделью**,
которая сама по себе дороже прежней (точный поиск вместо приблизительного
сглаживания): то есть корректность выросла, а стоимость упала.

## Что осталось нетронутым и почему

- **`stepWarships` (4.3 % тика)** — каждый корабль перебирает все суда в поисках
  цели, то есть O(n²). У OpenFront для этого есть `UnitGrid` — пространственный
  хэш по клеткам, дающий «соседей в радиусе» без полного перебора. При нынешнем
  числе судов (десятки) это не проблема; если флоты вырастут до сотен — начинать
  надо здесь.
- **`spreadBuildCell` (4.7 %)** — выбор клетки под постройку методом
  farthest-point: перебор выборки своих клеток × свои здания. Вызывается только
  когда бот реально строит, и уже ограничен `newB < 4` за ход.
- **Генерация карты** (~14 % профиля) — одноразовая, при старте комнаты.
