# Оптимизация рендера: дроны

Клиент рисует **60 кадров в секунду**, сервер тикает 10 раз в секунду. Поэтому цена
одного дрона в кадре умножается на 60 — и рой в несколько сотен машин легко съедает
кадровый бюджет целиком.

## Что было

Рой «Мопед» — до `DRONE_COUNT_MAX = 300` дронов на залп, и залпов бывает несколько
одновременно. На **каждый дрон каждый кадр** делалось:

- `save()` / `restore()`,
- `translate()` + `rotate()` (матричные операции),
- сборка строки цвета `rgb(r,g,b)` — аллокация,
- **три отдельных пути** (фюзеляж, крылья, хвост), каждый с `fill()` и `stroke()`.

Замер на реальной партии (два роя навстречу, 392 дрона в воздухе):

| | на кадр |
|---|---|
| вызовов к контексту | **10 976** |
| из них тяжёлых `fill`/`stroke` | 2 352 |
| чистого JS (без растеризации) | 0.109 мс |
| при 60 fps | ~6.5 % одного ядра только на дроны |

Плюс сеть: `dronesPub` отдавал массив ОБЪЕКТОВ, то есть ключи `"x"`, `"y"`, `"a"`,
`"owner"` повторялись в JSON 392 раза — **14.9 КБ за тик**, или ~300 КБ/с исходящего
трафика при двух игроках.

## Что сделано

### 1. Кэш заранее повёрнутых спрайтов

Самолётик рисуется **один раз** в offscreen-канвас для каждого сочетания
«цвет владельца × размер × поворот» (`SPRITE_ANGLES = 24`, то есть шаг 15° — на глаз
неотличимо). В кадре остаётся **один `drawImage` на дрон**: без матричных операций,
без смены состояния контекста, без аллокаций. Спрайты рендерятся с учётом `dpr`,
поэтому картинка не мылится на retina.

### 2. LOD на отдалении

При `size ≤ DRONE_DOT_SIZE_MAX = 5` пикселей (а на полностью отдалённой карте размер
модельки как раз упирается в минимум) детали самолётика физически не видны. В этом
режиме дроны рисуются точками `fillRect`, сгруппированными по владельцу — `fillStyle`
ставится один раз на группу, а не на дрон.

### 3. Мемоизация цвета

`playerColorCSS(id)` кэширует строку. Это касается не только дронов: ту же функцию
на каждый объект каждый кадр вызывают суда, боевые корабли и подписи.

### 4. Плоский массив вместо объектов

`dronesPub` отдаёт `number[]` по 4 числа на дрон: `[x·10, y·10, курс·100, владелец]`
— целые, без ключей и десятичных точек. Клиент раскладывает их в переиспользуемые
`Float32Array`/`Int16Array` (буферы не пересоздаются каждый тик), а рендер читает
типизированные массивы вместо массива объектов.

## Результат

| | было | стало |
|---|---|---|
| вызовов к контексту на кадр | 10 976 | **392** (близко) / 395 (отдалённо) |
| JS на кадр | 0.109 мс | **0.003 мс** / 0.005 мс |
| доля ядра при 60 fps | ~6.5 % | **~0.2 %** |
| трафик на тик | 14.9 КБ | **5.7 КБ** |
| `dronesPub` + JSON на сервере | 0.153 мс | **0.019 мс** |

Замер JS-части честный, но **неполный в пользу правки**: он не учитывает
растеризацию, а именно там разница ещё больше — вместо 2 352 заливок и обводок
контуров браузер делает 392 блита готовой картинки.

## Дальше — трейд-корабли

К ним применима та же схема: сейчас `drawShips` на каждое судно делает `beginPath` +
`arc` + `fill` + `stroke` и строку цвета (последнее уже подешевело от мемоизации).
Группировка по владельцу и точки/спрайты вместо `arc` дадут тот же порядок выигрыша.

# Оптимизация трейд-судов и сетевого кадра

Начал с судов, но замер показал, что дело шире: **весь кадр состояния весил ~67 КБ на
тик**, то есть примерно **670 КБ/с на каждого подключённого клиента**. Это и есть
причина просадок при онлайне — клиенту нужно каждый тик распарсить всё это, а
серверу — собрать и отправить каждому.

## Рендер судов

Судов бывают сотни (в замере 400 при 43 портах). Было: `beginPath` + `arc` + `fill` +
`stroke` и две установки стиля на каждое судно каждый кадр, причём `fillStyle`
собирался строкой.

Сделано как у дронов: кружок с обводкой отрисован заранее в offscreen-канвас (кэш по
владельцу и радиусу), в кадре — один `drawImage` на судно. На сильном отдалении
(радиус ≤ `SHIP_DOT_RADIUS_MAX = 3`) — точки, сгруппированные по владельцу.

| | было | стало |
|---|---|---|
| вызовов к контексту на кадр | 2 401 | **400** |
| JS на кадр | 0.048 мс | **0.002 мс** |

## Сетевой кадр

Четыре правки, все — «убрать то, что не меняется или не нужно»:

| раздел | было | стало | что сделано |
|---|---|---|---|
| **игроки** | 35.1 КБ | **4.9 КБ** | имя и флаги статичны — уходят один раз (`playersMeta`), в тик едут только числа плоским массивом |
| **здания** | 24.3 КБ | **6.5 КБ** | плоский массив целых вместо объектов со строковым типом и дробными прогрессами |
| **суда** | 26.5 КБ | **5.2 КБ** | плоский массив, координаты округлены (летели с 13 знаками после запятой) |
| **лодки** | 5.1 КБ | **3.1 КБ** | маршрут не меняется за рейс — шлётся один раз, клиент кэширует по id |

Итого: **средний кадр 67 → 18 КБ на тик**, исходящий трафик на клиента
**670 → 180 КБ/с**. При десяти игроках это разница между 6.7 и 1.8 МБ/с у сервера, и
ровно во столько же раз меньше работы у каждого клиента на `JSON.parse`.

Формат проверен «кругом»: собрал данные обратно точно так, как это делает клиент, и
сверил с состоянием игры — 293 игрока, 172 здания, 88 судов, расхождений **0**;
маршрут лодки приходит в первой посылке и отсутствует во второй, а после
`resendBoatPaths()` (вызывается при входе нового клиента) приходит снова.

## Что осталось

- **`roads` 5.1 КБ** — дорожная сеть заводов, шлётся раз в 500 мс. Меняется редко;
  можно отдавать только при изменении подписи, как `playersMeta`.
- **Дельты вместо полных списков.** Здания и игроки почти не меняются между тиками:
  если посылать только изменившиеся записи, останутся единицы килобайт. Это уже
  требует протокола с версионированием — отдельная работа.
- **Бинарный формат.** JSON тратит байты на скобки и запятые даже для чисел;
  `ArrayBuffer` дал бы ещё примерно вдвое.

# Как это устроено у OpenFront (и что оттуда взято)

Проверил по их коду (`src/core/Schemas.ts`, `src/core/worker/WorkerClient.ts`), а не
по памяти. У них принципиально другая схема — **детерминированный lockstep**:

- сервер шлёт клиенту только `Turn { turnNumber, intents[], hash }`, то есть **сами
  команды игроков**: `attack`, `spawn`, `boat`, `build_unit`, `donate_gold`,
  `cancel_attack`, `move_warship` и т.п.;
- каждый клиент **сам считает всю симуляцию** — в Web Worker
  (`WorkerClient.sendTurn(turn)`), главный поток только рисует;
- `hash` состояния на конец хода нужен, чтобы поймать расхождение симуляций.

Отсюда их масштабируемость: трафик — `O(числа действий)`, а не `O(размера мира)`.
Сколько бы ни было юнитов, по сети едут только приказы.

**Почему мы так не можем сегодня.** Наша симуляция **не детерминирована**: `Math.random()`
раскидан по всей игре (выбор клетки во фронте атаки, разброс дронов, решения ботов,
генерация карты). У них для этого сеяный `PseudoRandom`. Перевод на lockstep — это
переписать netcode и сделать симуляцию воспроизводимой до последнего бита, плюс
обработка расхождений. Отдельный крупный проект, а не правка; браться за него внутри
задачи «оптимизировать корабли» было бы нечестно.

**Что взято из их подхода прямо сейчас** — та же идея «шли только изменения»:

| | было | стало |
|---|---|---|
| здания | 24.3 КБ каждый тик | **дельтой, 0.16 КБ/тик** (в 39× меньше) |
| игроки | 35.1 КБ | 4.9 КБ (статика — один раз) |
| суда | 26.5 КБ | 5.2 КБ |
| лодки | 5.1 КБ | 3.1 КБ (маршрут — один раз за рейс) |
| дороги | 5.1 КБ раз в 500 мс | только при изменении сети |

**Итог: средний кадр 67 → 11.3 КБ на тик, трафик 670 → 113 КБ/с на клиента.**
При десяти игроках сервер отдаёт 1.1 МБ/с вместо 6.7 МБ/с — почти в шесть раз меньше.

Дельта зданий устроена как у нас уже сделаны дельты клеток: сервер помнит последнюю
отправленную строку каждого здания и шлёт только изменившиеся плюс id исчезнувших.
Страховки от рассинхронизации две: полная посылка раз в 10 секунд и принудительная
полная посылка при входе нового клиента (иначе он не увидел бы здания, построенные до
подключения). Проверено прогоном 600 тиков подряд на одних дельтах: расхождений с
состоянием сервера — **0**.

## Web Worker: замерил и НЕ стал делать

Собирался переносить разбор сообщений в worker — у них главный поток занят только
рендером. Сначала замерил на настоящих кадрах, сколько это стоит у нас:

| | мс на кадр | мс в секунду (10 кадров/с) |
|---|---|---|
| `JSON.parse` всего кадра | 0.025 | **0.25** |
| применение дельт карты | 0.001 | 0.01 |

**Итого 0.27 мс из 1000.** Переносить это в worker бессмысленно: рефакторинг
рискованный, а экономия — четверть миллисекунды в секунду. Не сделал.

Замер попутно вскрыл то, что я раньше не мерил вовсе, — и оно оказалось главным.

## Дельты клеток: 84% кадра

Когда я мерил разделы кадра, поле `changes` (какие клетки сменили владельца) я
подставлял пустым. На самом деле именно оно и было кадром: **71.9 КБ, из которых
60.5 КБ — дельты клеток**. При 293 ботах фронты двигаются постоянно, и за тик
меняются тысячи клеток.

Формат был «список пар»: `[клетка, владелец, клетка, владелец, ...]`. Сравнил четыре
кодировки на настоящих данных (2857 изменённых клеток за тик):

| кодировка | размер | выигрыш |
|---|---|---|
| как было: пары | 31.2 КБ | — |
| сортировка + разности индексов | 16.8 КБ | 1.9× |
| **+ RLE подряд идущих одного владельца** | **1.5 КБ** | **21×** |
| бинарно, varint (теоретически) | 0.7 КБ | 47× |

Взял RLE: `[Δначало, длина, владелец, ...]`, где начало серии — разность от начала
предыдущей. Работает так хорошо потому, что индексы клеток построчные, а фронт
захватывает клетки длинными горизонтальными рядами. Бинарный формат дал бы ещё вдвое,
но требует своего протокола — при уже полученных 21× это следующий шаг, не этот.

Проверено «зеркалом»: 500 тиков подряд применял только RLE-дельты к копии карты и
сверял с состоянием сервера — расхождений **0 клеток из 1 728 000**.

## Итог по трафику

| | было | стало |
|---|---|---|
| средний кадр | **71.9 КБ/тик** | **11.8 КБ/тик** |
| трафик на клиента | 719 КБ/с | **118 КБ/с** |
| при 10 игроках сервер отдаёт | 7.2 МБ/с | **1.2 МБ/с** |
| разбор на главном потоке клиента | 0.86 мс/с | **0.27 мс/с** |

## Что осталось из их арсенала

1. **Бинарный формат** вместо JSON — дельты клеток дали бы ещё ~2×, весь кадр примерно
   столько же. Требует своего фрейминга поверх WebSocket.
2. **Дельты игроков** — сейчас раз в 500 мс уходит полный список (4.9 КБ). Тот же
   приём, что со зданиями, урежет и это.
3. **Детерминированная симуляция + lockstep** — их модель целиком. Самое дорогое по
   работе и самое выигрышное по трафику.
